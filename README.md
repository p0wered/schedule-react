# Расписание

React-приложение с автоматической загрузкой расписания группы **648М** РГРТУ.

При каждом открытии страницы браузер запрашивает `/api/schedule.php`. PHP-обработчик на NAS (или локальный Node.js-сервер)
загружает [текущую неделю](https://rasp.rsreu.ru/schedule-frame/group?faculty=4&group=2265)
и ближайшую опубликованную неделю противоположной чётности. Предпочтение отдаётся
следующей неделе; если она ещё не опубликована — предыдущей. Числитель и знаменатель
определяются по подписям самого сайта. Даты недель хранятся внутри данных, но не
отображаются в колонках.

Во время загрузки отображается skeleton в форме карточек расписания. Полностью
совпадающие занятия в двух неделях объединяются в одну карточку: сравниваются
название, тип, преподаватель и аудитория. Это сравнение опубликованных недель,
а не утверждение, что занятие повторяется весь семестр.

Длинные названия в карточках сокращаются по словарю `src/lib/disciplineNames.ts`.
Полное название доступно в подсказке при наведении. Исходные данные и сравнение
занятий используют полные названия; неизвестные словарю предметы отображаются
полностью.

Под расписанием по центру отображается время последней **успешной загрузки обеих недель** по Москве.
При ошибке запроса или неожиданной разметке сохраняется последняя успешная версия
с исходным временем обновления и появляется сообщение об ошибке. Сервер хранит
её вне каталога сайта во временной папке PHP; Node.js использует
`.cache/rsreu-648m.json`. Браузер хранит свою копию в `localStorage`. Если сохранённого
расписания ещё нет, приложение показывает ошибку и ссылку на источник. Если
сохранённые недели не включают текущую, подсветка текущих занятий отключается.

Сервер запрашивает источник при каждом новом запросе; одновременно поступившие
запросы используют одну загрузку. Автоматического обновления долго открытой вкладки
нет — для нового запроса нужно перезагрузить страницу. Актуальность ограничена
тем, что университет опубликовал на своём сайте.

## Локальный запуск

Требуется **Node.js 22.12+** (ветка 22 или более новая LTS).

```shell
npm ci
npm run dev
```

Открыть `http://127.0.0.1:5173`. Одна команда запускает API и Vite.

```shell
npm run typecheck
npm run lint
npm run test
npm run build
npm start
```

`npm start` обслуживает production-сборку из `dist` и API одним сервером.
`npm run preview` предназначен только для просмотра статической сборки и не
запускает API расписания.

## NAS / Web Station — основной способ размещения

Новый Node.js-сервер, контейнеры и платный backend не нужны. В сборке есть
самостоятельный обработчик `api/schedule.php`. PHP выполняется на NAS через
Web Station, а браузер обращается к API на том же домене.

Для исходящего HTTPS к РГРТУ обработчик использует `api/cacert.pem` — набор
корневых сертификатов Mozilla с [официального сайта curl](https://curl.se/docs/caextract.html).
Проверка цепочки сертификата и имени сервера включена. Это позволяет не зависеть
от старого или ненастроенного набора CA на NAS и не менять системный `php.ini`.
Файл PEM загружается вместе с папкой `api`; без него загрузка расписания завершится
ошибкой. Источник, версия, лицензия и проверенная SHA-256 указаны в
`api/cacert.NOTICE.txt`. При обновлениях приложения набор CA нужно актуализировать
из того же источника и сверять с опубликованной контрольной суммой.

### Подготовка сайта schedule2415.ru

Эти действия **ещё не выполнены на NAS**. Перед заменой файлов сохраните локальную
копию текущего сайта и снимок настройки его виртуального хоста.

1. В **Web Station → Настройки PHP** создайте **отдельный профиль** с именем,
   например, `Schedule PHP 7.4`. Выберите PHP **7.4** и включите расширение **curl**.
   Не редактируйте общие профили других сайтов. Требуются также DOM, libxml и JSON;
   проверка ниже покажет, доступны ли они. HTTPS использует TLS библиотеки cURL.
2. В **Виртуальный хост** выберите именно `schedule2415.ru` и назначьте созданный
   PHP-профиль. Сохраните прежние Nginx, корневой каталог `web`, порты 80/443
   и параметры HTTPS. Настройки других сайтов и панели DSM не меняйте.
3. Выполните `npm run build` и загрузите **содержимое** `dist` в корень этого
   сайта: `index.html`, `assets`, `api` и остальные файлы сборки. Если используете
   подготовленный ZIP, распакуйте его содержимое туда же. Папка `dist` внутри
   `web` не нужна. Сначала загрузите новые assets и api, затем index.html.
   Сохраните старые assets до проверки; не удаляйте другие файлы в `web`.
4. Откройте `https://schedule2415.ru/api/schedule.php?health=1`.
   Ожидается JSON, где **все значения true**:

   ```json
   {"phpSupported":true,"curl":true,"dom":true,"libxml":true,"json":true,"https":true}
   ```

   Эта проверка не загружает расписание и не создаёт кеш. Если виден текст PHP
   или файл скачивается, PHP не подключён к этому сайту. Если 404 — проверьте
   путь загрузки. Если какое-то значение false — проверьте отдельный PHP-профиль.
5. Откройте `https://schedule2415.ru/api/schedule.php`. Ожидается JSON с
   `stale: false`, `updatedAt`, двумя датами `weeks` и расписанием. Это проверяет
   реальное исходящее HTTPS-соединение NAS с университетом и разбор расписания.
   Если PHP не сможет записать кеш, успешные ответы продолжат работать,
   а причина появится в журнале PHP; серверного резерва до исправления не будет.
   Затем перезагрузите главную страницу: должны появиться расписание и время
   успешного обновления под ним.

Если проверка расширений проходит, а расписание не загружается, откройте
`/api/schedule.php?health=source`. Эта проверка скачивает обе недели и разбирает
HTML без записи кеша. При успехе возвращается `ok: true`; при ошибке —
`ok: false`, этап `stage` и сообщение `error`. Диагностический ответ использует
HTTP 200, чтобы Web Station не заменяла его своей общей страницей ошибки;
обычный API без кеша по-прежнему возвращает 503. Проверка не выдаёт PHP-трассировки
или настройки сервера. Не запускайте её многократно: каждый вызов обращается
к сайту университета.

Дополнительные порты и доступ к панели DSM для API не требуются. Адрес панели
с портом 5000 в приложение не добавляется. Если сайт используется по другому
адресу, проверки выполняются по этому адресу с теми же путями `/api/...`.

PHP хранит последний успешный JSON и файл блокировки в подпапке
`sys_get_temp_dir()` с именем `rsreu-schedule-…`. Папка должна быть доступна PHP
для записи и разрешена `open_basedir`. При очистке временных файлов или
перезагрузке NAS этот кеш может исчезнуть; браузерная копия остаётся.
Ошибки загрузки/парсинга возвращают сохранённый результат с `stale: true` и
**старым** временем обновления. Без кеша API возвращает 503. Подробности ошибок
пишутся в журнал PHP, а не в ответ браузеру.

Чтобы вернуть прежний сайт, восстановите его index.html и необходимые assets
из своей копии и прежний PHP-профиль **только этого** виртуального хоста.

### Проверка PHP локально

Обработчик использует синтаксис PHP 7.4. Для локальной проверки нужен PHP 7.4+
с curl, DOM, libxml, JSON и TLS в cURL:

```shell
npm run test:php
npm run build
npm run preview:php
```

Откройте `http://127.0.0.1:5174`. Это production-сборка с настоящим PHP API.
Тесты парсера и кеша также проверены локально на PHP 8.5; выполнение именно
в PHP 7.4 на NAS нужно проверить после назначения профиля и загрузки файлов.

## Необязательный запуск через Node.js

Существующий `npm run dev` остаётся для разработки, `npm start` — для размещения
на сервере с Node.js. В Node.js пути `/api/schedule.php` и `/api/schedule`
обрабатывает Node API; PHP там не требуется. `?health=1` предназначен только
для проверки обработчика PHP на Web Station или при `preview:php`.

Dockerfile и compose оставлены как дополнительный вариант, если впоследствии
понадобится контейнер. Для текущего размещения на NAS они не используются.

## Код

- `public/api/schedule.php` — автономный PHP API для Web Station: парсер, кеш и проверка окружения;
- `scripts/test-php.php` — PHP-проверки на сохранённой разметке и сбоях источника;
- `server/rsreu.ts` — загрузка и разбор HTML, сопоставление двух недель;
- `server/service.ts` — сохранение успешного результата и возврат кеша при ошибке;
- `server/index.ts` — API и обслуживание приложения;
- `src/hooks/useSchedule.ts` — загрузка при открытии страницы и браузерный кеш;
- `src/lib/scheduleSnapshot.ts` — проверка данных и чётность опубликованных недель.

Тесты парсера используют HTML, полученный с сайта 18 сентября 2026 года. При
изменении разметки сайта парсер может потребовать адаптации; неподдерживаемые
структуры, например несколько занятий в одной ячейке, вызывают ошибку вместо
сохранения неполного расписания.
